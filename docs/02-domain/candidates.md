# Кандидаты в классы предметной области

## Часть 1. Существительные из сценариев

Извлечены из `scenarios.md` (ВИ-01 «Управлять устройством», ВИ-04 «Получать уведомления»).

| Существительное | Решение | Почему |
|---|---|---|
| жилец | класс `Пользователь` с обобщением | есть идентичность, роль, жизненный цикл |
| взрослый | специализация `Пользователь` | отличается поведением (полные права) |
| ребёнок | специализация `Пользователь` | отличается поведением (ограниченные права + эскалация) |
| роль | атрибут или enum | конечный набор значений, не имеет своего жизненного цикла |
| права доступа | класс `ПолитикаДоступа` | правило меняется, зависит от роли и устройства |
| привилегии | атрибут `Пользователь.привилегии` | значение, не сущность |
| команда | класс `Команда` | есть жизненный цикл: создана → распознана → выполнена / отклонена |
| устройство | класс `Устройство` {abstract} | есть идентичность, состояние, история |
| целевое устройство | ассоциация `Команда → Устройство` | ссылка, не отдельная сущность |
| доступность устройства | атрибут `Устройство.доступно` | производное от состояния связи |
| состояние устройства | enum `Состояние` | конечный набор: ВКЛ / ВЫКЛ / ОШИБКА / ОФЛАЙН |
| событие | класс `Событие` | есть время, тип, источник — это сущность |
| журнал | класс `Журнал` | коллекция событий с жизненным циклом (ротация, очистка) |
| подтверждение | атрибут `Команда.подтверждена` | производное от факта получения ответа |
| канал доставки | класс `Канал` | разные каналы (Телеграм, SMS, push) с разным поведением |
| Телеграм-бот | не моделируем | внешняя система, не часть домена |
| Модуль «Пятница» | не моделируем | отдельный контейнер (микросервис), не доменная сущность |
| полиция | не моделируем | внешняя система, не часть домена |
| уведомление | класс `Уведомление` | есть жизненный цикл: сформировано → отправлено → доставлено / в очереди |
| тип события | enum `ТипСобытия` | конечный набор: штатное / аварийное |
| время | атрибут | свойство события или уведомления, не сущность |
| источник | ассоциация `Событие → Устройство` | ссылка, не сущность |
| очередь недоставленных | состояние уведомлений | не отдельный класс, а признак уведомления |
| резервный канал | атрибут `Канал.резервный` | производное от политики доставки |
| интервал подтверждения | атрибут `ПолитикаДоставки.интервал` | параметр, не сущность |
| аварийный датчик | разновидность `Датчик` | тот же датчик, отличается только логикой обработки сигнала |
| сигнал в полицию | класс `Уведомление` с типом «внешнее» | отдельная сущность не нужна, отличается адресатом |
| повышение привилегий | класс `ЗапросЭскалации` | есть жизненный цикл: запрошен → одобрен → активен → истёк |

**Примечание по «устройству».** В сценариях фигурирует абстрактное «устройство» без указания вида. Конкретные виды устройств выведены из него **обобщением** и описаны в части 2. Это осознанное решение: сценарии формулируются на уровне цели актёра («управлять устройством»), а не на уровне конкретной модели.

## Часть 2. Иерархия устройств

```
Устройство {abstract}
  + id : String
  + название : String
  + расположение : String
  + состояние : Состояние
  + производитель : String
  + модель : String
├── УправляемоеУстройство {abstract}
│   + включить() : void
│   + выключить() : void
│   ├── Свет
│   │   + яркость : int
│   │   + установитьЯркость(уровень : int) : void
│   ├── Замок
│   │   + заперт : boolean
│   │   + запереть() : void
│   │   + отпереть() : void
│   └── Климат
│       + целеваяТемпература : double
│       + установитьТемпературу(t : double) : void
└── Датчик {abstract}
    + последнееЗначение : double
    + времяПоследнегоСигнала : DateTime
    ├── ДатчикПротечки
    │   + обнаружитьПротечку() : void
    └── ДатчикДвижения
        + обнаружитьДвижение() : void
```

```
enum Состояние {
  ВКЛ
  ВЫКЛ
  ОШИБКА
  ОФЛАЙН
}
```

**Пояснения к решениям:**

- **`Устройство` — абстрактный класс.** «Просто устройство» не существует. Закрывает требование «хотя бы один абстрактный класс».
- **`УправляемоеУстройство` и `Датчик` — обобщение от `Устройство`.** Разные контракты: первое принимает команды, второе публикует данные. Датчик не управляется, поэтому в одну ветку с управляемыми не попадает.
- **`Свет`, `Замок`, `Климат` — классы по видам поведения.** У каждого свои операции и атрибуты, они не сводятся к одному классу с типом.
- **`ДатчикПротечки` и `ДатчикДвижения` — классы.** Порождают разные события, разное поведение.
- **Аварийный датчик — не отдельный класс.** Это тот же датчик, отличается только логикой обработки сигнала. Аварийность выражается через `ТипСобытия` и настройки `Сценария`, а не через новый класс.
- **Модель и производитель — атрибуты**, не отдельные классы. Каталога моделей в системе нет.

## Часть 3. Обновление по ПР2

При построении динамических моделей обнаружились расхождения, которых не было видно на статической модели ПР1. Они внесены в `domain.puml` отдельными коммитами.

| Что добавлено | Почему |
|---|---|
| Класс `Контроллер` | В рефлексии ПР1 система описана как центральный контроллер, но в модели классов его не было. Без него диаграммы последовательности опирались бы на абстрактную «Систему». |
| `СтатусКоманды` | У команды появился наблюдаемый жизненный цикл: создана → распознана → проверена → отправлена → подтверждена / отклонена / ошибка. |
| `СтатусСценария` | Флага `активно : boolean` недостаточно: нужны пауза, ошибка, архивирование и состояние «сработал». |
| `Сценарий.проверить/приостановить/возобновить/архивировать` | Операции, которые вызывают переходы автомата в части 3. |
| `Журнал.записать(Событие)` | На диаграммах команда и сценарий фиксируют события; в ПР1 у журнала были только `создать/очистить`. |
| `ВидУстройства.ДАТЧИК_ДЫМА` | Правило безопасности требует реакции на пожар; нужен источник аварийного события. |
| Состояние `Эвакуация` в автомате сценария | Опасность (например, пожар) прерывает сценарий, двери открываются, люди могут покинуть помещение. |

**Правило безопасности.** Любое опасное состояние, ведущее к ошибке (пожар, задымление, авария), обязано приводить к открыванию дверей и разблокировке замков. Это инвариант, который сильнее любого сценария автоматизации: сценарий прерывается, а эвакуация выполняется всегда.
