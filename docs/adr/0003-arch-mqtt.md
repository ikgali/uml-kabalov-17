# ADR-3. Для связи с устройствами используется MQTT, а не HTTP

**Дата:** 2026-11-15  
**Статус:** принято

## Контекст

Устройства умного дома — свет, замки, климат, датчики протечки, движения и дыма — общаются с системой по сети. У них разные возможности: датчики работают от батареек и просыпаются редко, actuators должны получать команду быстро, часть устройств находится за NAT и не имеет публичного адреса. Соединение нестабильно: Wi-Fi пропадает, устройства перезагружаются, пакеты теряются. Нужно выбрать протокол, который выдержит это без постоянного опроса и без потери команд.

## Рассмотренные варианты

1. **HTTP REST.** Привычен, хорошо инструментирован, но работает по модели «запрос — ответ». Сервер не может отправить команду спящему датчику, пока тот сам не пришёл; приходится либо постоянно опрашивать устройства (расход батареи и трафика), либо держать на каждом устройстве веб-сервер с публичным адресом. Заголовки HTTP тяжёлые для узкополосных каналов, а обрыв соединения не виден до следующего запроса.
2. **MQTT-брокер.** Публикация/подписка через посредника: устройства и Backend API не знают адресов друг друга. Есть QoS 0/1/2, retained-сообщения, последняя воля (LWT) для обнаружения обрыва, постоянные сессии и компактный заголовок. UDP-подобная экономичность при доставке через TCP, множество готовых клиентов для микроконтроллеров.
3. **WebSocket.** Двусторонний канал поверх TCP, удобен для браузера и чата. Но это транспорт без готовой семантики доставки: QoS, retained-сообщения, last will и авторизацию по топикам пришлось бы проектировать самостоятельно. Сервер держит состояние каждого соединения, а для батарейных устройств постоянный WebSocket всё равно слишком дорог.

## Решение

Вариант 2: MQTT. В системе появляется брокер Eclipse Mosquitto как отдельный контейнер. Backend API публикует команды в топики устройств, устройства публикуют телеметрию и подтверждения; для команд и важной телеметрии используется QoS 1, для частых показаний допустим QoS 0. LWT переводит устройство в состояние `ОФЛАЙН`, если оно пропало. HTTP остаётся для Телеграм-бота, «Пятницы», Полиции и служебного API — там, где нужна обычная request-response-семантика.

## Последствия

**Плюсы:** устройства могут спать и выходить на связь по расписанию; команда доставляется без публичного адреса устройства; брокер развязывает отправителя и получателя; QoS и LWT дают предсказуемую обработку обрывов; трафик и энергопотребление ниже, чем при HTTP-опросах.

**Минусы:** брокер становится критической точкой — нужны кластеризация, резервный узел и мониторинг; требуется настроить TLS, аутентификацию и ACL по топикам, иначе одно устройство сможет читать чужие команды. Появляется дополнительная сущность в эксплуатации, а отладка распределённой доставки сложнее, чем у прямого HTTP-вызова.

**Что станет неверным, если решение пересмотреть:** C4 L2 (контейнер «Брокер MQTT»), динамическая диаграмма и диаграмма развёртывания, `workspace.dsl`, а также этот ADR. Переход на HTTP потребует либо постоянного опроса, либо публичных адресов и веб-серверов на устройствах, что противоречит их энергетическим и сетевым ограничениям.
