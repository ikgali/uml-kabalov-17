# ADR-2. «Пятница» — отдельный контейнер, а не компонент Backend API

**Дата:** 2026-11-15  
**Статус:** принято

## Контекст

Голосовой модуль «Пятница» принимает голосовую команду, переводит речь в текст, выделяет намерение и целевое устройство и передаёт результат в Backend API. В ПР1 он был описан как «внутренний голосовой интерфейс», а в ПР2 на диаграмме последовательности упоминался только в примечании как альтернативный канал. При переходе к C4 нужно было решить, является ли он компонентом внутри Backend API или самостоятельным контейнером.

Ключевое отличие от остальных компонентов — технологический стек: распознавание речи требует Python-библиотек и ML-моделей (Whisper/PyTorch), тогда как Backend API написан на Kotlin/Spring Boot. Кроме того, голосовой модуль потребляет GPU и память непропорционально остальной системе.

## Рассмотренные варианты

1. **Компонент внутри Backend API.** Один деплой, один процесс, нет сетевого вызова между распознаванием и оркестрацией. Но Python-модели пришлось бы запускать рядом с JVM (отдельный процесс или JNI), образ API вырос бы до гигабайтов, а масштабирование GPU-нагрузки потянуло бы за собой весь API.
2. **Отдельный контейнер (микросервис).** «Пятница» собирается в собственный образ, развёртывается отдельно, масштабируется по нагрузке и может работать на узлах с GPU. С API общается по HTTPS, контракт — «распознанная команда».
3. **Внешний облачный сервис распознавания речи.** Не нужно сопровождать ML-модели, но голосовые данные уходят третьей стороне, появляется зависимость от сети и тарифа, а задержка и доступность не контролируются.

## Решение

Вариант 2: «Пятница» — отдельный контейнер внутри границы ИС «Умный дом», развёрнутый как самостоятельный сервис на Python/FastAPI. Backend API не знает, как устроено распознавание; он получает от «Пятницы» уже нормализованную команду и дальше применяет ту же политику доступа, что и для Телеграм-бота. На C4 L2 это отдельный `Container`, на C4 L3 — внешний по отношению к Backend API элемент.

## Последствия

**Плюсы:** независимые релизы и масштабирование, GPU-нагрузка изолирована, падение или деградация распознавания не блокирует команды из Телеграм-бота, у каждого сервиса свой стек и свои метрики. Контракт «команда» позволяет позже заменить модель или целиком вынести распознавание в облако.

**Минусы:** появляется сетевой хоп и ещё одна точка отказа; нужны аутентификация между сервисами, трассировка запроса через два процесса, отдельный CI/CD и мониторинг. Образ с ML-моделями тяжёлый, а холодный старт дольше, чем у Kotlin-сервиса.

**Что станет неверным, если решение пересмотреть:** диаграммы C4 L2/L3 и динамическая диаграмма, `workspace.dsl`, схема развёртывания (под `friday`), а также этот ADR. При возврате «Пятницы» внутрь API придётся объединять Python- и JVM-сборку и пересматривать требования к узлам кластера.
